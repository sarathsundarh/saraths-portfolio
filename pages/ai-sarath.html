How I built the portfolio assistant

The chat on my homepage answers questions about my work in my voice, lists the facts each answer used, and can scroll the page to them. This is how the shipped version works, how I tested it, and where it falls short.

Why build it at all

A chatbot that restates a résumé adds nothing. It earns its place only if it does three things a static page can't: answer the specific question you came with, show where the answer came from, and say "I don't have that" instead of guessing.

So the goal was narrow: grounded, checkable, and cheap enough to leave running.

Architecture

There's no streaming. The function returns one JSON object, and the browser types the answer out word by word for readability. If the API is down or rate-limited, the three suggested questions fall back to scripted answers, and anything else gets a short "email me" message.

One source of truth

Everything the assistant knows is 23 hand-written facts in one file (api/_kb.js). Each has an id, a title, the page section it belongs to, and a public link where one exists. They cover my roles, projects, education, skills, awards, availability and this assistant. The same file generates llms-full.txt, so what crawlers read and what the chat answers from can't drift apart.

What I left out matters as much: my phone number, eligibility details and internal notes never enter the knowledge base, so the model can't leak what it was never given.

Retrieval: BM25, on purpose

For 23 short facts, a vector database is more machinery than the problem needs. BM25 returns the top 7 facts for each question, plus a profile fact that is always included, with no second API key and results I can reason about.

Its weakness showed up in testing: "What roles are you seeking?" missed the availability fact because that fact never used the words "roles" or "seeking". The fix was to write the fact the way people ask, not to add embeddings. If paraphrase misses keep appearing, a small embedding pass is the next step.

Citations you can check

Gemini answers in JSON mode with a schema: answer, citations (an enum of the fact ids) and action. The server keeps only citations that were in the retrieved set, so a model can't cite a fact it never saw. What's left renders as chips under the answer; click one and the page scrolls to the source and circles it.

Moving the page

There's one "tool", and it's deliberately small: the schema's action field can name one place on the page (a section, a project card or an experience item), or none. The browser maps that to an anchor, scrolls there, and draws a marker circle. Nothing runs on the server besides retrieval, and the model can't open links or navigate away.

Guardrails

  • It answers in my voice, but says it's an AI assistant that can make mistakes when asked, and never claims to be me.
  • It answers only from the facts. Missing one, it says so and points to my email.
  • It never invents metrics, tools or outcomes, and keeps team credit as written. Asked who built which part of a team project, it says the facts don't break that down.
  • No added feelings or filler ("I'm proud", "passionate"). Early answers had them, so the prompt now forbids them and the evals check every answer.
  • Visa, work-authorization and salary questions go to email.
  • It ignores instructions inside pasted text and declines unrelated requests.

Cost and abuse limits

Input is capped at 1,000 characters and the last 12 messages. Requests are limited to 8 a minute and 60 an hour per IP (in memory, so best effort across serverless instances), and the model call times out after 15 seconds. It runs on the cheapest Gemini Flash-Lite model. When Google retired the model I'd configured, the function started returning 404s. It now falls back to an available Flash-Lite model, and GET /api/chat reports which model is live.

Evals

scripts/eval.mjs sends 17 fixed questions to the live endpoint and checks each answer with patterns: facts that must appear, claims that must not, and required citations. Trap questions check that it refuses to guess, for example "What was your GPA at USC?" (not in the facts) and "Did you win Cal Hacks?" (2nd place in Anthropic's track, not overall). Every answer is also checked for filler words. The latest run is saved to evals/last-run.json in the repo.

What these evals don't show

  • 17 cases is a smoke test, not a benchmark. Pattern checks can pass a vague answer or fail a correct one phrased differently.
  • Each case runs once against a non-deterministic model, so a pass isn't a guarantee the next answer will pass.
  • Timeouts are real: one of the first 17 requests hit the 15 second cap.
